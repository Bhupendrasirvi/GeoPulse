Chapter 1: Project Overview & Problem Statement

Emergency situations such as road accidents, fire outbreaks, and urban floods require immediate assistance. In emergency management, every minute counts toward saving lives and reducing damage.

1.1 Background & Practical Problem

In most cities and regions, conventional emergency handling depends on manual telephone helplines. When callers contact control rooms under panic, several practical problems occur:

  • Unclear Landmark Descriptions: Callers often struggle to convey exact street names or landmarks, especially in flooded or unfamiliar areas.
  • Manual Team Search: Dispatchers have to manually call or look up which team is free, resulting in dispatch delays.
  • No Real-Time Map Overview: Coordinators lack a single live map showing open emergencies alongside active responder units.

1.2 Project Solution

GeoPulse is a practical web application built to solve these exact problems. It provides a clean portal where citizens can submit distress alerts with one-click GPS coordinate capture, and a centralized operations dashboard where emergency coordinators can view all incidents on a live map and match them with the nearest available rescue unit in seconds.

Chapter 2: System Requirements & Technologies Used

GeoPulse was built using lightweight, modern web technologies ensuring that the application can run on any standard personal computer or local server without complex setup.

Chapter 3: System Architecture & Workflow

GeoPulse is structured as a standard 3-tier client-server application. Each layer handles a distinct responsibility, keeping the code clean, modular, and easy to maintain.

3.1 Three-Tier Architecture Layers

  • Presentation Layer (Frontend): Web browser interface containing the SOS reporting form, status counters, incident list, and the Leaflet interactive crisis map.
  • Application Layer (Node.js API): Express server that exposes REST endpoints (/api/incidents, /api/match, etc.), parses JSON payloads, and communicates with MongoDB.
  • Data Layer (MongoDB): Houses collections and executes the $geoNear aggregation pipeline using spherical distance calculations.
Figure 3.1: GeoPulse 3-Tier System Architecture Diagram

3.2 Complete Project Workflow

  1. Citizen SOS Submission: The user opens the web app, enters contact details, selects an emergency type (Fire, Medical, Flood), and clicks on the map to set their GPS pin.
  2. Database Insertion: The backend receives the POST request and saves the incident as a GeoJSON Point in MongoDB.
  3. Dispatcher Proximity Matching: The dispatcher clicks 'Match Unit'. Node.js executes a $geoNear query searching within 15 km.
  4. Assignment & Visual Route Line: The closest squad is assigned and a dashed route line connects the team to the victim.
  5. Resolution: When the rescue squad reaches the victim and provides assistance, the dispatcher clicks 'Resolve'.

4.2 Indexing Strategy

  • db.incidents.createIndex({ location: '2dsphere' }): Allows MongoDB to perform spherical distance calculations on incident coordinates.
  • db.responders.createIndex({ location: '2dsphere' }): Enables fast indexing of responder vehicle locations.
  • db.incidents.createIndex({ resolvedAt: 1 }, { expireAfterSeconds: 172800 }): TTL index that automatically purges resolved incidents after 48 hours.

Chapter 5: Proximity Search & $geoNear Engine

Finding the closest rescue unit to an emergency is the most critical function of GeoPulse. Rather than calculating distances in JavaScript loops, the query runs directly inside MongoDB using the $geoNear aggregation stage.

Figure 5.1: Proximity Search Pipeline & Execution Flow

5.1 The $geoNear Pipeline Code (server.js)

const pipeline = [
  {
    $geoNear: {
      near: { type: 'Point', coordinates: [parseFloat(incidentLng), parseFloat(incidentLat)] },
      distanceField: 'distanceMeters',
      spherical: true,       // Calculates real-world distance on Earth's curved surface
      maxDistance: 15000,    // Search within 15 km radius
      query: { status: 'Available' }
    }
  },
  { $limit: 3 } // Returns top 3 candidate units with distance
];
const nearest = await db.collection('responders').aggregate(pipeline).toArray();

5.2 How $geoNear Works

  1. Spherical Distance: By setting spherical: true, MongoDB uses spherical geometry calculations to compute distance in meters directly across the globe.
  2. Status Filter: The query: { status: 'Available' } clause ensures only squads that are currently free are considered.
  3. Distance Limit: The maxDistance: 15000 restricts matches to within 15 km, preventing distant units from being dispatched unnecessarily.
  4. Fast Sorting: MongoDB automatically outputs the matching records pre-sorted by ascending distance, so the first document is guaranteed to be the closest.

Chapter 6: Fallback Auto-Assignment & Report Stacking

Real-world emergency response systems must handle edge cases gracefully, such as distress calls from remote rural sectors where no active unit is nearby, or multiple calls reporting the same disaster.

6.1 Fallback Auto-Provisioning

If an emergency occurs in an unstaffed area and nearest.length === 0 (no pre-registered squad exists within 15 km), GeoPulse does not leave the victim unattended. Instead, the backend automatically creates a local emergency volunteer response squad nearby and assigns it to the incident:

if (!nearest || nearest.length === 0) {
  // Auto-provision a local emergency response squad nearby
  const fallbackUnit = {
    id: 'R-AUTO-' + Date.now().toString().slice(-4),
    name: 'Local Emergency Rapid Response Team',
    type: 'Volunteer Rescue Team',
    status: 'Assigned',
    contact: '+91 98000-00112',
    location: { type: 'Point', coordinates: [incidentLng + 0.008, incidentLat + 0.006] }
  };
  await db.collection('responders').insertOne(fallbackUnit);
  assignedSquad = fallbackUnit;
}

6.2 Report Stacking for Disaster Zones

During major incidents like a building collapse or factory fire, dozens of nearby citizens may submit distress calls for the same location. Showing 20 individual markers on the map would clutter the view and confuse dispatchers.

  • Grouping Logic: The frontend detects incident pins that share nearby coordinates within a small threshold (~200m).
  • Aggregated Badge: Overlapping calls are visually consolidated into a single card showing a badge like x3 reports, combining the total victim count while keeping the map clear.

Chapter 8: Dynamic Route Vector & ETA Projection

Once a rescue team is matched to an incident, dispatchers and responders need an immediate visual reference of the travel trajectory, physical distance, and estimated travel time.

8.1 Dynamic Route Vector Display

Figure 8.1: Dynamic Proximity Route Vector Connecting Rescue Squad to Victim

8.2 Distance & ETA Calculation

The system calculates the straight-line spherical distance $D$ using MongoDB's output (in meters). Estimated Time of Arrival (ETA) is then computed based on average urban emergency vehicle travel speed:

// Distance and ETA Calculation in frontend map controller
const distanceKm = (responder.distanceMeters / 1000).toFixed(1);
const averageSpeedKmH = 35; // Estimated emergency response vehicle speed
const etaMinutes = Math.max(2, Math.round((distanceKm / averageSpeedKmH) * 60));

// Display popup on route polyline
polyline.bindPopup(`<b>Dispatched Unit:</b> ${responder.name}<br/>
<b>Distance:</b> ${distanceKm} km<br/>
<b>Estimated Arrival:</b> ~${etaMinutes} mins`).openPopup();

Chapter 11: How to Run, REST APIs & Conclusion

GeoPulse is completely self-contained and easy to set up on any computer with Node.js and MongoDB installed.

11.1 How to Run the Project

  • Step 1: Start MongoDB service: net start MongoDB (Windows) or sudo systemctl start mongod (Linux).
  • Step 2: Open terminal in geopulse-backend/ and start the backend: node server.js.
  • Step 3: Open your browser to http://localhost:5000. (You can also double-click start.bat in the project root to start everything with one click).
